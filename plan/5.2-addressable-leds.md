# Lightinator 5.2: Addressable LEDs and Virtual Lights

**Status:** Initial feature plan; proposed contracts and limits need validation
before implementation. This is not a description of current behavior.

## Goal and scope

Add FastLED-backed addressable LED strings alongside existing analog PWM
virtual lights. A digital virtual light can address portions of one or more
physical strings, show the normal color-corrected light output or run an
independent pixel effect, and explicitly blend with an adjacent digital light.
All digital hardware, light, overlap and effect configuration must be possible
both in the webapp and in the native Home Assistant integration.

Target ESP32-family builds first, consistent with the
[shared-codebase strategy](esp8266_esp32_shared_strategy.md); preserve ESP8266
behavior and builds without adding FastLED to that target. Host-side tests should
exercise the shared model without requiring LEDs. The precise SoCs, chipsets,
pixel formats and capacities supported in 5.2 are a feasibility and release
gate, not assumed properties of FastLED.

## Starting point

- [VirtualLight](../include/virtuallight.h) owns an `RGBWWLed` instance.
  [APPLedCtrl](../app/ledctrl.cpp) resolves configured PWM pins and owns ESP32
  PWM banks. The library computes color and animations but currently writes to
  PWM-oriented outputs; digital output needs a real integration seam, not a
  second, divergent implementation of normal color behavior.
- `hardware.configuration.lights` in [app-config.cfgdb](../app-config.cfgdb)
  currently describes pin-based lights. Selected board profiles, SoC
  capabilities and other pin users participate in validation. Configuration
  uses `GET /config` and partial `POST /config`; arrays are not implicitly
  merged by light ID. The
  [5.1 contract](../plan-multiLightLedCtrl.prompt.md) notes that reload
  validation currently follows the ConfigDB commit, so rejection can leave
  invalid persisted configuration.
- Light IDs and numeric indexes are stable; an omitted light selector chooses
  the configured default. Do not equate index with array position. Preserve
  existing analog command, transition, scene, preset and event behavior.
- The [webapp](https://github.com/pljakobs/esp_rgb_webapp2) and
  [native HA integration](https://github.com/pljakobs/Lightinator_HA_module) are separate projects
  with existing virtual-light editors and integrations. The firmware also has
  legacy HA MQTT discovery; its present main/channel behavior is not equivalent
  to the native integration's full configuration UI.
- ConfigDB sources and generated API projections are governed by
  [API_SCHEMA.md](../API_SCHEMA.md). New fields need coordinated firmware,
  generated schemas and client releases.

## Proposed user-visible model

### Physical strings

Define each digital string once, independently of virtual lights, with a stable
ID, board-allowed output pin, LED chipset/protocol, pixel count and color order.
Add any required clock pin only for protocols that actually support it. Describe
pixel format and any white channel explicitly; do not assume all FastLED
chipsets support RGBW or the same transport. A string is one physical output
resource and may be used by multiple digital lights.

The board profile/catalog and SoC pin checks must describe digital-capable
outputs and restrictions; a catalog template alone must not grant an invalid
GPIO. Claim each physical data/clock pin once against PWM, other strings,
buttons, I2C, system pins and target-specific peripherals. Make an empty digital
configuration valid.

### Virtual lights and segments

Retain existing analog light definitions and stable IDs/indexes/default rules.
Introduce an explicit backend discriminator for new digital lights, with a
backward-compatible interpretation for existing analog records. A digital light
contains an ordered list of segments referencing string IDs and **zero-based,
half-open** base intervals `[start, end)`; each segment may specify direction.
One light can span multiple strings and can have multiple disjoint segments.
Segment order and direction define its logical pixel sequence for effects;
physical string order defines lower/upper for adjacency. Show both meanings in
the clients. Validate missing strings, empty or out-of-bounds intervals,
duplicate membership, invalid direction and resource limits.

Base intervals are exclusive: arbitrary overlapping ranges are invalid. An
explicit neighbor relationship is the only way to share pixels. Gaps are
allowed and render black unless claimed by another light. A physical output is
transmitted once per frame after all its lights are composed, not independently
by each virtual light.

### Explicit spatial overlap

The following is a **proposed** deterministic 5.2 contract for review, not an
existing schema. A segment may choose its immediate lower or upper neighbor on
the same string and request an overlap of `N` pixels. The adjacent segments
must have touching base intervals; gaps, non-neighbors and cross-string links
are rejected. A light spanning strings can have a separate relationship on each
applicable segment. A segment may have one lower and one upper neighbor, provided
their blend bands do not intersect. Each physical pixel may have at most two
contributors; reject triple intersections and invalid or oversized overlaps.

Represent each boundary once as a canonical relationship between two stable
segment identities and a pixel count. Clients display the corresponding
lower/upper setting on **both** lights. Creating, editing or removing it from
either side updates the single relationship atomically; the reciprocal view is
derived, never a second independent value that can drift. Deleting a segment,
light or string must either remove its affected relationships in the same
confirmed transaction or reject the operation with a clear explanation.

For a concrete geometry, propose that the `N` shared pixels straddle the
boundary: the last `ceil(N/2)` base pixels of the lower segment and first
`floor(N/2)` of the upper segment. Both lights render those physical pixels;
each segment's effective interval extends into its neighbor accordingly. Reject
an overlap that does not fit either segment or conflicts with another band.
For effects, render/sample using each light's effective sequence, including
these shared pixels, so both contributors have a defined pixel value. This
changes effective effect length when an overlap changes and must be visible to
the user.

For shared pixels ordered from lower light A toward upper light B, with
`i = 0 .. N-1`, propose `wB = (i + 1)/(N + 1)` and `wA = 1 - wB`.
Mix each output channel as `round(wA * A[i] + wB * B[i])`, with sufficient
intermediate precision and saturation. For `N=10`, B contributes approximately
9%, 18%, ... 91% (A contributes the complement); `N=1` is 50/50. Adjacent
non-overlapped pixels are 100% their owning light. Mixing identical inputs
preserves that input, independent of render order.

Blend each light's rendered frame, whether static, transitioning or animated,
at the same stage and color depth before final output quantization. An off
light contributes black at its assigned weight: the neighbor does not gain
ownership, so the band dims rather than being renormalized. This produces a
spatial fade, not synchronization of two independent effects. If a selected
effect cannot supply per-pixel frames to the compositor, it must be unavailable
for overlap rather than silently bypassing blending. Confirm the geometry,
curve and off behavior with the user before freezing the contract.

## Rendering, color and effects

1. Separate logical state/animations and color conversion from the physical
   output backend. Reuse the existing RGBWW color/white-balance and brightness
   pipeline for normal digital lighting and transitions. Do not run both
   RGBWW correction and an equivalent FastLED correction a second time.
2. Define supported pixel formats and explicitly map the corrected channels to
   the physical format, including a calibrated white strategy for RGB-only
   pixels and RGBW only if the selected backend supports it. An RGB pixel cannot
   reproduce separate analog warm/cool-white emitters exactly; document the
   mapping and supported color modes rather than promising identical light.
   Keep raw channel commands and readback unambiguous per supported format.
3. Give each light its own logical state, mode, transition and effect state.
   Build a frame for each contributing light, composite overlaps, apply any
   clearly specified output-only scaling/quantization, and submit one coherent
   frame per physical string. Avoid exposing a FastLED global brightness or
   correction setting as an accidental second per-light control.
4. Integrate FastLED as a pinned, license-compatible Sming component with a
   target-specific transport. FastLED provides pixel primitives and platform
   drivers; it is not assumed to provide a ready-made catalog of named effects.
   Define a curated, versioned set of FastLED-based effects and parameter
   schemas, with stable IDs, defaults, ranges and capability reporting. Prove
   per-light instance isolation, effect-on-effect and effect-on-static blends.
5. Specify mode switching, on/off, brightness, transitions, effect parameter
   changes, stop/queue interactions, presets/scenes and reboot restoration.
   Report logical per-light state and selected effect, not a fictitious single
   color sampled from an animated or blended output. Unsupported operations
   must report an explicit error and must not corrupt state.

Before committing to the architecture, prototype the selected FastLED release
on the actual Sming/ESP-IDF toolchain and intended SoCs. Verify runtime pin and
protocol selection: if FastLED requires compile-time template registrations,
provide a bounded dispatch registry and expose only combinations actually
built. Measure refresh time, heap, allocation peaks and interference with PWM,
networking, watchdogs and interrupts. Account for physical buffers, per-light
effect buffers, overlap/segment metadata and temporary reload allocations.
Set and publish defensible per-target limits from measurements, including a
minimum usable frame rate and largest supported configurations; never silently
truncate a strip or claim unsupported configurations work.

## Configuration and integration contract

### Firmware and API

- Extend the authoritative persistent and transient ConfigDB schemas and API
  metadata; regenerate the projections and update the version/compatibility
  contract. Keep existing analog configurations readable without rewriting IDs,
  indexes, pin assignments or default-light semantics.
- Provide one authoritative topology validator for all configuration sources.
  Merge a partial update with current configuration, validate the entire
  candidate (including reciprocal overlap, pin conflicts, effect support and
  capacity), then commit atomically. Do not rely on current post-commit reload
  rejection. Define concurrency/version conflict handling so two clients do not
  accidentally overwrite array edits; return actionable validation paths/errors.
- Stage allocations/resources before activation and preserve current running
  and persisted configuration on preparation failure. Define and test the
  safe state, error/event and recovery if a hardware failure occurs after
  detachment. Reconfiguration and shutdown must stop frame work, respect
  in-flight transfers and release physical resources safely. Unchanged lights
  should retain state and animation where their resources remain compatible.
- Expose target/board capabilities, actual limits, supported protocols, pixel
  formats, effects/parameters and per-light supported controls. Ensure indexed
  command/readback and per-light state/change notifications work for all
  backends and all clients; reconcile current default-only spontaneous events.
  Define how old clients behave on unknown digital types and unavailable
  features rather than letting them overwrite unfamiliar configuration.
- Update catalogs/templates and API/runtime documentation; keep generated
  schemas and frontend validators in sync. Define backup/restore, upgrade and
  downgrade behavior, including explicit rejection or a recovery path when an
  older firmware cannot safely read a digital configuration.

### Webapp

Extend the existing virtual-light and board configuration workflows to create,
edit and delete physical strings and digital lights; select protocols, pins,
pixel count/order and segments across strings; set direction and effect options;
and edit overlaps from either neighbor. Visualize physical string positions,
gaps, base/effective spans, reciprocal overlaps and the gradient. Show target
limits, supported options and server validation errors; prevent conflicts but
keep firmware validation authoritative. Save dependent changes as one candidate,
handle concurrent edits and refresh actual configuration after success or
failure. Provide effect selection, parameters and per-light state in the
normal control UI, with translations and accessibility.

### Home Assistant

Extend the existing native integration's virtual-light configuration workflow
and panel/options/services as appropriate so HA users can perform the same
configuration operations as the webapp, including strings, multi-string
segments, direction, both sides of overlap, deletion and effect parameters.
Use the same firmware configuration contract and surface errors and concurrent
updates; do not require editing YAML or visiting the webapp. Document the
supported HA UI/service interaction for every setting.

Expose one stable HA light entity per virtual light, with only its supported
color modes, brightness and effect list. Route commands and updates using the
stable light identity/index; handle effects, on/off, availability, rename,
deletion and reconnect without stale entities or feedback loops. Keep
configuration of physical topology separate from ordinary light commands.
The firmware's MQTT discovery is a separate, legacy integration path: preserve
existing users and specify/test its multi-light and effect support or explicit
limitations. It must not be presented as a substitute for the required native
HA configuration workflow.

## Delivery milestones

1. **Feasibility and decisions:** validate FastLED/Sming and hardware on each
   candidate SoC; measure capacity and transport behavior; agree pixel formats,
   overlap geometry/color space, starter effects and supported board matrix.
   Produce a tested minimum frame-rate and memory budget for release targets.
2. **Contract and safety foundation:** define schemas, capability negotiation,
   candidate validation and transactional persistence/reload; add compatibility
   fixtures and ensure analog-only upgrades and older-client behavior work.
3. **Digital static output:** implement physical string ownership, segments,
   normal color pipeline and per-light control/events; verify mixed PWM/digital
   operation and safe reconfiguration before introducing effects.
4. **Overlap compositor:** implement canonical relationships, reciprocal views,
   validation, frame blending and deterministic host tests; verify static and
   transitioning lights on hardware.
5. **Effects:** implement the agreed FastLED-based set, state/parameters and
   per-light frame rendering; verify effects across segments and overlaps.
6. **Cross-project delivery:** implement webapp and native HA configuration and
   controls, schema synchronization and compatibility tests; handle MQTT
   discovery compatibility. Coordinate releases across all three projects.
7. **Release qualification:** complete hardware, soak, upgrade/recovery and
   end-to-end testing, document limits and publish compatible release versions.

## Verification and release gates

- Host/unit tests: interval validation and mapping for multiple strings,
  direction, gaps and boundaries; invalid GPIO/protocol/capacity combinations;
  unique IDs/indexes/default; reciprocal updates/deletion; overlap `N=1`,
  `N=10`, odd/even/max sizes, both ends of a middle segment, triple-overlap
  rejection, render-order independence, equal inputs and off behavior.
- Golden pixel frames: static/static, transition/static, effect/static and
  effect/effect; segmented and reversed sequences; channel precision, clamping,
  color correction exactly once, RGB/white conversion and per-string output.
- API/integration tests: atomic candidate failure without persistent or runtime
  mutation, activation failures, concurrent writers, reboot and backup/restore,
  analog migration, older clients, explicit capability errors, per-light
  state/events, effects, scenes/presets, HA discovery cleanup and reconnect.
- Webapp and HA tests: full create/edit/delete workflows, multiple strings,
  configuring either side of an overlap and seeing the mirrored side, validation
  and conflict errors, effect controls, refresh/restart and compatibility with
  older firmware. Run shared API fixtures against all three projects.
- Physical tests on every advertised SoC/protocol/board combination: color
  order and white mapping, independent overlapping lights, effects, mixed PWM,
  multiple strings, power cycles, reconfiguration, network traffic, OTA and
  sustained maximum supported load. Measure refresh rates, heap headroom,
  watchdog stability and timing; verify actual electrical output. Publish the
  measured configurations and limits, not just successful builds.
- Build and regression gates include Host, ESP32-family and unchanged ESP8266
  builds, existing PWM/virtual-light tests, schema generation and relevant
  webapp/HA suites. Hardware-dependent claims require hardware evidence.

## Decisions to resolve before implementation

1. Which ESP32 SoCs, boards, LED chipsets, RGB/RGBW formats and minimum
   pixel/string counts are required for 5.2? Is a clocked protocol in scope?
2. Approve or revise the proposed boundary-centered overlap geometry,
   interpolation curve, off behavior and maximum two contributors. Should
   adjacency ever cross separate physical strings?
3. What calibrated RGB-only white/CT behavior and color space for blending are
   acceptable? Which controls should be exposed per pixel format?
4. Which initial effects and adjustable parameters are release requirements?
   What persistence and transition behavior is expected when modes change?
5. What minimum frame rate and headroom are required at the supported maximum
   pixel counts? Select limits only after target measurements.
6. Which HA configuration UI is preferred for complex topology, and what
   operational support beyond backward compatibility is required for MQTT
   discovery? Define the precise older-firmware/client compatibility matrix.
